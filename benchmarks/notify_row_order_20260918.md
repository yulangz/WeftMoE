# Notify expert 内行序实验（2026-09-18）

本轮检验：在最终专家贡献按固定 expert ID 顺序归约的前提下，能否用原子计数直接分配 expert 内行号，省掉本地稳定排序。基线为已采用本地 dX 双 tile 领取的生产源码，完整源码哈希保存在 `results/notify_row_order_20260918/manifest.json`。所有候选先在独立源码快照中构建。

## 数值问题的范围

对前向 `Y = XW` 而言，排列 X 的行只是排列独立输出行；保持每行内部 K 累加方式，再按 route 映射返回原 token，即可恢复相同结果。固定最终 expert 合并顺序可以避免网络到达次序影响浮点加法。因此，固定 expert 内输入行序并不是前向 batch invariance 本身的必要条件。

反向权重梯度则沿 token 行归约，例如 `dW1 = Xᵀ dAB`、`dW2 = Uᵀ dR`（具体权重存储方向不影响这一归约关系）。在这些 GEMM 中，token 行成为 K 归约维度；重排行会重排乘积的累加次序。数学上的和不变，但 FP32 累加及最终 BF16 舍入可能变化。最终 token 的 expert 合并顺序无法约束这条独立的 dW 归约。

## 候选实现

- **baseline**：现有 `local_notify`，每 1024 条 route 按 `(expert, 原位置)` 分组排序，二分查找组内 expert 区间起点，再累加更早 chunk 的计数得到稳定 `local_offset`。
- **atomic**：清零每个 expert 的 histogram，每条有效 route 用 `atomicAdd(histogram[expert], 1)` 的返回值作为 `local_offset`。保留 expert/rank/node 描述、top-k `combine_order`、错误检测以及后续全局布局、wave 和本地消费顺序生成。不同 worker 的原子到达次序可以改变行排列。
- **runs**：保留 baseline 的排序和 chunk 前缀，删除逐项二分查找。排序后标记每个 expert 区间首项的位置，对位置做 inclusive max scan，将最近的区间起点传播到每项，再以 `position - start` 得到区间内序号。该方法支持任意 expert ID 范围，不需要按 expert 数分配额外共享数组。

本轮只改变本地 `local_offset` 的生成方式。后续路由消费顺序的排序以及每 token 的 expert 合并顺序均保留。

## 原子分配的数值对照

Qwen，EP8，每 rank 129 tokens，E16/top-k8，H2048/I512。每次独立进程重新运行 Notify、Forward 和 Backward；不是只对同一份 Forward 检查点反复做 Backward。各次输入、路由、gate、上游梯度均逐字节一致。

| 对照 | dX 不同元素 | dgate 不同元素 | dW1 不同 BF16 元素 | dW2 不同 BF16 元素 |
|---|---:|---:|---:|---:|
| baseline → atomic 第一次 | 0 | 0 | 3,087 / 33,554,432 | 1,755 / 16,777,216 |
| atomic 第一次 → atomic 第二次 | 0 | 0 | 918 / 33,554,432 | 488 / 16,777,216 |
| baseline → runs | 0 | 0 | 0 | 0 |

baseline/atomic 的 dW1、dW2 最大绝对差分别为 `6.103515625e-5`、`3.0517578125e-5`；atomic 两次运行分别为 `1.52587890625e-5`、`3.0517578125e-5`。这属于浮点次序造成的小幅差异，但已经不满足逐位一致要求。不能把这种失败描述成完整训练确定性通过。

atomic 的 canonical X/A/B 排列确实不同；这是预期的内部布局变化，不能将其本身视为数值失败。对外梯度中的 dW 差异才是这里的判据。runs 的全部 80 份输入、检查点及梯度文件与 baseline 逐字节相同。

另对 Qwen EP8/8K、E256/top-k8 的完整 Forward 做 20 次全输出重复检查，每次重新运行 Notify。atomic 的重复检查通过，最终全输出哈希与 baseline 相同；输入、gate、route 和实际权重存储哈希亦相同。该检查支持用户提出的前向判断，不能外推到尚未检查的全部模型与跨节点配置。

原始张量、逐文件差异计数和日志位于 `results/notify_row_order_20260918/`，由 `probe.py` 和 `compare.py` 生成。性能对照与这些数值检查分开执行，正式计时移除 `WEFTMOE_BENCH_CHECK_REPEAT`。

## 性能对照与采用决定

Qwen EP8，E256/top-k8，8K/64K 两个配置。每个配置依次测试 baseline、atomic、runs，第二轮反转配置和实现顺序；每次 10 次预热、30 次正式计时，共 360 个正式样本。每次调用取各 rank 的最大耗时，wall 包含 Notify、张量申请/输入克隆和保留反向状态的 Forward；rank barrier 在计时外。GPU 工作串行，正式计时期间没有构建或数值校验作业。

本机 8 卡 SM 设置为 1620 MHz，每个运行前后记录时钟和限频标志，结束解除锁频。本轮没有逐调用窗口的连续时钟监控，不宣称每个周期恒频，也不把微小差异当成稳定收益。下表用全部 60 个样本的标准中位数（偶数时取两个中间值平均）；原生日志的 P50 取值规则不同，因此末位可能略有差别。保留全部离群值。

| tokens/rank | 方案 | 完整调用 P50 (ms) | 相对基线耗时改善 | Notify P50 (µs) | 相对基线耗时改善 |
|---:|---|---:|---:|---:|---:|
| 8,192 | baseline | 2.987305 | — | 453.1205 | — |
| 8,192 | atomic | 2.980370 | +0.232% | 442.1665 | +2.417% |
| 8,192 | runs | 2.996310 | -0.301% | 461.0160 | -1.742% |
| 65,536 | baseline | 19.915850 | — | 1010.0400 | — |
| 65,536 | atomic | 19.976800 | -0.306% | 1023.3750 | -1.320% |
| 65,536 | runs | 19.907700 | +0.041% | 1003.9200 | +0.606% |

atomic 在 8K 下完整调用的两轮改善分别为 -1.353% 和 +0.524%，方向不一致；64K 则分别为 -0.313% 和 -0.301%。因此，省掉本地排序没有在这组完整算子对照中带来稳定加速。原子竞争和行分配变化都可能影响开销；本轮没有用独立微基准或 trace 将具体原因分离，不作单一归因。

runs 在 8K 下两轮完整调用分别回退 0.129% 和 0.849%；64K 的两轮改善为 -0.099% 和 +0.087%，合并后仅 +0.041%。其数值保持一致，但没有足够性能收益支持替换生产代码。

**采用决定：保留当前 baseline；atomic 和 runs 均未采用。** 默认沿用完整前后向逐位一致的要求：atomic 已被独立 Notify 重跑中的 dW 差异否决；runs 没有显示稳定的完整调用优势。因此没有继续扩展这两个候选的 Flash/EP16 性能矩阵，也没有为候选放宽元数据或梯度测试。

这次实验验证了“前向逐行 GEMM 不要求固定 expert 内行序”的判断，同时明确了它与训练 dW 确定性的区别。若以后单独定义允许 dW 浮点差异或纯推理的接口，可以重新评估非稳定分配；当前对照还不能据此声称原子分配就是更快的实现。

[机器记录](notify_row_order_20260918.json)汇总对照、源文件一致性和采用决定。实验完成后按用户要求删除 atomic、runs 两个候选的源码快照、构建目录以及生成候选代码的脚本；保留测量日志、数值对照、分析脚本与结论。记录中的候选二进制路径属于历史运行信息，已不能直接重跑；`compare.py` 和 `summarize.py` 仍可分析保留的数据。本轮 GPU 作业已结束，生产 `src` 保持实验前原样。
