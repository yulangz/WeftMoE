**训练 X 保存与缓冲区复用，2026-09-17，1620 MHz**

前向八种配置中七种 wall 中位数改善 1.36%–3.70%，另一个 Flash EP16/8K 中位数略慢 0.19%、均值改善 0.08%。反向中位数变化为 −0.32% 到 +0.19%，接近持平。每卡 pool 减少 256 MiB–3 GiB，batch/EP 一致性与保留状态验证通过。

本轮基线已经包含稳定 radix 区间优化和 mapped host 完成通知；以下收益只衡量本轮新增修改。

## 具体实现

### 1. 将保存 X 融入 FC1 已有的数据读取过程

训练反向需要保留路由后的输入 X。旧实现中，FC1 从资源池的 canonical X 区读取输入，训练 FC2 写入另一块临时输出区；kernel 结束后，再通过独立的 D2D 拷贝把 canonical X 保存到调用者持有的检查点。这样既要额外读取一次 X，也必须让原始 X 占用资源池空间直到拷贝结束。

现在 FC1 读取 X 到共享内存后，直接从该共享 stage 写入调用者的检查点。代码分工如下：

| 位置 | 新增或修改的职责 |
|---|---|
| [forward/kernel_contract.cuh](../src/cuda/forward/kernel_contract.cuh)，`ForwardKernelArgs` | 传入调用者的 `saved_x` 指针和 `saved_x_map` TMA 描述符。 |
| [activation_transport.cu](../src/cuda/activation_transport.cu)，Forward enqueue | 为有数据的训练调用建立保存 X 的 BF16 TMA store map；普通计算路径不再提交 kernel 后的 X D2D 拷贝。 |
| [persistent_v3/forward/compute_kernel.cuh](../src/cuda/persistent_v3/forward/compute_kernel.cuh)，`persistent_role` | 在 FC1 的 K 循环内保存已经就绪的共享 X stage。 |
| [forward/kernel_support.cuh](../src/cuda/forward/kernel_support.cuh)，`make_layout` | 将训练 FC2 输出地址设为 `layout.canonical_rows`，省去独立输出区的分配。 |

这里 M block 是一组输入行，N tile 是一组输出列，K iteration 是矩阵乘法的一段输入列。相同 M block 的各个 N tile 都会读取 X，因此只让 `n_tile == 0` 保存，避免同一输入被重复写入。每个 K iteration 保存对应列段，覆盖完整 X；保存的是已有 BF16 数据，没有再次量化。

### 2. 完整 tile 与 expert 尾部采用不同写法

完整 128 行 tile 在 `fc1_full[stage].wait(phase)` 确认输入就绪后，由线程 0 发出 `SM90_TMA_STORE_2D::copy`。目标坐标是当前 K 列段和当前 compact 行号，数据直接来自现有共享内存。TMA 写入与同一 stage 的矩阵读取可以重叠。

expert 最后一块不足 128 行时，改由 math threads 分工执行 `uint4` 向量写入，一次保存 8 个 BF16。每次检查 `m < valid_rows` 和列边界，并通过 `m128_fragment_vector_offset` 从共享内存布局找到源数据。不能简单对尾部发出完整 tile store：compact 行没有按 expert 补齐 128 行，这会跨到下一个 expert，读到尚未就绪的数据或写出调用者实际行数。

### 3. 用完成依赖保护共享 stage 和缓冲区复用

完整 tile 的 TMA issuer 在向 stage 的 empty barrier 到达之前，执行 `cp.async.bulk.wait_group 0`，等待本组 TMA 写入完整完成。原有 WGMMA 等待继续保护矩阵读取。因此共享 stage 重新装入下一轮输入时，上一轮的矩阵读取和检查点保存均已结束。

已有 FC1→FC2 调度依赖要求同一 M block 的全部 FC1 N tile 退休后，FC2 才能开始。此时该 block 的 X 已保存，且所有 FC1 读取已结束，所以 FC2 可以覆盖同一块 canonical 空间。生命周期为：

```text
资源池 canonical 区：路由后的 X → FC2 输出 → 反向临时 dR
调用者检查点：       FC1 保存 X ─────────→ 后续反向读取 X
```

检查点由调用者持有，不能随资源池复用而失效；A/B 的保存方式以及 gates/headers 的原有拷贝保持不变。上述保存代码受 `RetainBackwardState` 编译期条件控制。`WEFTMOE_BENCH_TRANSPORT_ONLY` 跳过 FC1，因此该诊断模式保留旧 X 拷贝和独立预填充输出区，避免把诊断夹具覆盖。

### 4. 收益如何对应到实现

速度收益来自去掉一次完整 X 的独立 D2D 保存，把保存动作放进已有 FC1 读取流程；新增 TMA store 本身仍有写流量和等待成本，因此没有声称保存 X 免费。显存收益来自删除独立训练输出区，其大小为 `max_destination_rows_per_rank × max_hidden_size × sizeof(BFloat16)`，本轮配置对应每卡 256 MiB–3 GiB。调用者仍需分配 X/A/B 和输出张量，下面报告的是内部 pool 的减少量。

FC1/FC2 的数学表达式、BF16 检查点转换及归约顺序未改变。仅保留“完整 tile 用 TMA、尾部用向量写入、完整等待后回收 stage”的实测版本；全向量保存和延迟写等待等候选的结果在后文单独列出。

独立候选试验：

- 全部 tile 使用普通向量保存 X：Qwen EP8/8K wall P50 3.083890 → 3.085375 ms，Flash EP8/64K 55.9364 → 56.03695 ms，未采用。
- 完整 tile 改用 TMA，暂不复用缓冲区：对应两项为 3.086215 → 2.995960 ms、55.95645 → 55.28095 ms。
- 将每步完整 TMA 等待改为只等源读取，直到 FC1 任务末尾再等写入完成，没有稳定收益。复用缓冲区后的对照中，Qwen GPU P50 完整等待/延迟写等待为 2.49736/2.49232 ms，Flash 为 54.0579/54.0770 ms；保留同步规则更简单的完整等待。

每步 `cp.async.bulk.wait_group 0` 等待 TMA 写入完成，然后 issuer 才向 shared stage 的 empty barrier 到达。[NVIDIA PTX 文档](https://docs.nvidia.com/cuda/parallel-thread-execution/#data-movement-and-conversion-instructions-cp-async-bulk-wait-group)区分了完整完成等待和只等待源读取的 `.read` 形式。expert 尾部不能使用未经掩码的完整 tile store，否则可能读到尚未就绪的相邻 expert 并越过调用者实际行数。

验证：

- Qwen、Flash 各 160 份 Forward/Backward 张量与既有参考逐字节一致，包括保存的 X/A/B、dX、dgate、dW1、dW2。
- 两模型的 EP8×258 与 EP16×129 重分片后，输出及输入/route/gate 逐字节一致；共同 129-token 前缀在 EP8 的 129/258/8K/64K batch 中一致，EP16 的 8K/64K 前缀一致。
- 两模型 × EP8/EP16 × 8K/64K，每 rank 20 次全输出重复校验通过，输入、输出、路由、gate、权重哈希与冻结基线一致。
- 同样八种配置的反向，每 rank 三次全梯度重复校验及额外 CPU 全量重复比较通过；四种最终梯度哈希与本轮基线一致。大尺寸跨版本比较使用哈希，小尺寸参考使用逐字节比较。
- 两模型的动态路由 graph、跨 stream 消费、均匀/完全偏斜路由、空 rank、资源池扩容，以及复用后的旧保留状态反向通过。
- EP1/EP2 元数据、非法输入恢复、取消/deadline、API allocation audit；EP8/EP16 rank 0 故障传播；仅通信诊断的重复输出检查通过。
- Compute Sanitizer memcheck：Qwen、单卡、E8/top-k8、129 tokens，覆盖完整 tile 和 1 行尾部，三次梯度重复校验，设备内存错误为零。禁用 API 错误报告是为了排除 NCCL 已知且被处理的架构探测调用；这不是“所有 CUDA API 零错误”的声明，也不覆盖全部多 GPU 并发交错。

后续独立试验将 FC1 gate/up 合并为原生 N256 指令，每个 K 步从 8 条 N128 变为 4 条 N256，寄存器数不变。两模型各 160 份前后向张量逐字节一致；两个 EP8 试测 case 的 GPU 中位数额外改善约 0.47%（Qwen/8K）和 0.28%（Flash/64K）。这些试测未纳入本报告的正式候选；后续已完成的独立全矩阵验证见 [N256 报告](fc1_packed_20260917.md)，组合试验见 [FC1 组合报告](fc1_combined_20260917.md)。原始试测仍保存在本报告的机器记录中。
